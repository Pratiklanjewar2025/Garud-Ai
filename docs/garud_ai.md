# 2. GARUD-AI Project Definition

GARUD-AI CyberShield is a Generative AI-powered Android APK security
investigation platform.

The platform receives potentially suspicious Android APKs and performs a
complete security investigation.

GARUD-AI combines:

1.  APK Intake
2.  File Validation
3.  SHA-256 Hashing
4.  APK Metadata Extraction
5.  Certificate Analysis
6.  Malware DNA Fingerprinting
7.  Threat Memory
8.  Reverse Engineering
9.  Static Analysis
10. Dynamic Analysis
11. Network Analysis
12. IOC Extraction
13. Feature Correlation
14. Cybersecurity RAG
15. Vector Search
16. Knowledge Graph Analysis
17. Agentic AI Investigation
18. MITRE ATT&CK Mapping
19. Risk Scoring
20. Malware/Fraud Classification
21. Campaign Correlation
22. Explainable AI
23. Automated Report Generation
24. Threat Memory Update

The goal is not simply to say:

> "This APK is malicious."

The goal is to explain:

-   What the APK is.
-   What the APK contains.
-   What the APK does.
-   What suspicious behavior was observed.
-   Which infrastructure it communicates with.
-   Whether it resembles previously analyzed malware.
-   Which malware family it may belong to.
-   Which fraud campaign it may be associated with.
-   Which MITRE ATT&CK techniques are supported by evidence.
-   How dangerous the APK is.
-   Why the system reached its conclusion.
-   What actions the security team should take.

# 3. Core Problem

Fraudulent and malicious Android applications can be distributed
through:

-   WhatsApp
-   SMS
-   Telegram
-   Phishing websites
-   Third-party APK websites
-   Social engineering
-   Malicious links
-   Fake banking websites
-   Fake UPI applications
-   Fake loan applications
-   Fake investment applications
-   Fake government applications
-   Fake reward applications

Malicious applications may perform:

-   Credential theft
-   OTP theft
-   SMS interception
-   Contact harvesting
-   Accessibility abuse
-   Screen monitoring
-   Overlay attacks
-   Device information collection
-   File access
-   Data exfiltration
-   Command-and-control communication
-   Remote command execution
-   Fraudulent transaction assistance
-   Banking credential theft

Traditional security tools can produce large amounts of technical
information.

The problem is that an investigator still has to correlate:

-   Static evidence
-   Dynamic evidence
-   Network evidence
-   Threat intelligence
-   Historical malware
-   IOCs
-   Malware families
-   Campaign relationships

GARUD-AI automates this correlation and investigation.

# 4. Core Philosophy

GARUD-AI must follow this principle:

``` text
RAW APK
   ↓
SECURITY ANALYSIS
   ↓
EVIDENCE
   ↓
FEATURE CORRELATION
   ↓
THREAT INTELLIGENCE
   ↓
AI REASONING
   ↓
RISK SCORING
   ↓
CLASSIFICATION
   ↓
REPORT
```

The system must NOT be designed as:

``` text
APK → LLM → Malicious
```

Instead:

``` text
APK
 ↓
Deterministic Security Tools
 ↓
Structured Evidence
 ↓
RAG + Knowledge Graph
 ↓
AI Agents
 ↓
Explainable Decision
```

LLMs should reason over evidence generated by security tools rather than
replacing the malware-analysis tools.

# 7. Storage Architecture

GARUD-AI must use different storage systems for different types of data.

## 7.1 PostgreSQL

Use PostgreSQL for structured information.

Store:

-   Users
-   APK metadata
-   Sample IDs
-   SHA-256
-   Certificate information
-   Analysis status
-   Static findings
-   Dynamic findings summary
-   Network findings summary
-   IOCs
-   Risk scores
-   Confidence scores
-   Severity
-   Classification
-   Malware family
-   Investigation records
-   Report metadata

------------------------------------------------------------------------

## 7.2 MinIO / S3

Use object storage for large binary and analysis artifacts.

Store:

-   Original APK
-   Decompiled source
-   Smali files
-   Extracted resources
-   PCAP files
-   Screenshots
-   Runtime logs
-   Large JSON artifacts
-   HTML reports
-   PDF reports

Example:

``` text
garud-apks/
└── 2026/
    └── 08/
        └── GARUD-APK-000001/
            ├── original.apk
            ├── metadata/
            ├── decompiled/
            ├── static/
            ├── dynamic/
            ├── network/
            ├── screenshots/
            └── reports/
```

------------------------------------------------------------------------

## 7.3 Qdrant

Use Qdrant for vector data.

Store:

-   APK embeddings
-   Malware behavior embeddings
-   Threat report embeddings
-   Threat Memory embeddings
-   Malware similarity vectors
-   Historical investigation embeddings
-   Knowledge base embeddings

Qdrant answers:

> "What previous threats are semantically similar to this APK?"

------------------------------------------------------------------------

## 7.4 Neo4j

Use Neo4j for relationships.

Example:

``` text
APK
 ↓
uses
 ↓
Domain
 ↓
resolves_to
 ↓
IP
 ↓
associated_with
 ↓
Malware Family
 ↓
part_of
 ↓
Campaign
```

Store relationships between:

-   APKs
-   Hashes
-   Certificates
-   Domains
-   URLs
-   IPs
-   Malware families
-   Campaigns
-   MITRE techniques
-   Threat actors where supported by validated intelligence
-   Fraud patterns

------------------------------------------------------------------------

## 7.5 Redis

Use Redis for:

-   Cache
-   Session information
-   Job status
-   Temporary analysis state
-   Agent workflow state
-   Rate limiting
-   Queue coordination

Redis is NOT the permanent source of truth.

------------------------------------------------------------------------

## 7.6 Elasticsearch

Use Elasticsearch for:

-   Runtime events
-   Network events
-   DNS events
-   Security logs
-   IOC search
-   Threat hunting
-   Analysis events
-   High-volume searchable telemetry

# 8. Primary APK Object

Every uploaded APK must receive a unique internal identifier.

Example:

``` text
GARUD-APK-000001
GARUD-APK-000002
GARUD-APK-000003
```

This `sample_id` is the primary application-level identity.

All storage systems should reference this ID.

Example:

``` text
GARUD-APK-000001
    ├── PostgreSQL
    ├── MinIO/S3
    ├── Qdrant
    ├── Neo4j
    └── Elasticsearch
```

# 10. Stage 2 --- APK Upload

## Input

Binary APK file.

Example:

``` text
FakeBank.apk
```

HTTP request:

``` http
POST /api/v1/apks/upload
Content-Type: multipart/form-data
```

Form fields:

``` text
file
source
optional description
```

## Processing

The backend:

1.  Receives the file.
2.  Creates a sample ID.
3.  Creates an analysis record.
4.  Stores the original APK.
5.  Starts the analysis workflow.

## Output

``` json
{
  "sample_id": "GARUD-APK-000001",
  "status": "UPLOADED"
}
```

## Storage

PostgreSQL:

``` text
sample_id
original_filename
source
upload_time
status
```

MinIO/S3:

``` text
original.apk
```

# 48. AI Model Architecture

GARUD-AI should have an LLM abstraction layer.

Example:

``` text
GARUD-AI LLM SERVICE
        |
        ├── NVIDIA NIM
        ├── OpenAI-compatible API
        ├── Groq
        ├── Local Model
        └── Other Supported Provider
```

The selected LLM should be configurable.

Do not hard-code agent logic to one provider.

The LLM is used for:

-   Reasoning
-   Evidence correlation
-   Threat explanation
-   Investigation
-   Report generation
-   Natural-language interpretation

The LLM is NOT responsible for:

-   Executing APKs
-   Replacing static analysis
-   Replacing dynamic analysis
-   Calculating raw cryptographic hashes
-   Directly determining truth without evidence
-   Inventing IOCs

# 57. Security Requirements

Because GARUD-AI executes potentially malicious applications, security
isolation is mandatory.

The malware analysis environment should have:

-   Isolated Android emulator/VM
-   Network isolation
-   Resource limits
-   CPU limits
-   Memory limits
-   Execution timeout
-   File-system isolation
-   No production credentials
-   No production database access
-   Controlled network egress
-   Automatic environment cleanup
-   Per-analysis reset
-   Audit logging

Dynamic analysis must never be allowed to compromise the main GARUD-AI
infrastructure.

# 70. Golden Rule for AI Coding Agents

Before modifying GARUD-AI code, an AI coding agent must:

1.  Read this specification.
2.  Understand the complete APK lifecycle.
3.  Identify the affected service.
4.  Identify the input schema.
5.  Identify the output schema.
6.  Identify the correct database/storage system.
7.  Preserve `sample_id` across the entire pipeline.
8.  Preserve evidence provenance.
9.  Avoid duplicating functionality.
10. Avoid bypassing the analysis pipeline.
11. Never store APK binaries directly in PostgreSQL unless explicitly
    required.
12. Never execute untrusted APKs outside the isolated analysis
    environment.
13. Never allow an LLM to invent security evidence.
14. Maintain backward-compatible APIs where possible.
15. Add tests for every new pipeline component.
